# CR-007: Provision a `memberships` row for new Supabase Auth users

**Requester:** Claude (frontend)
**Status:** open

## User need

A real customer needs to be able to sign up for an account and immediately use the app — book a
service, message their mechanic, and so on.

## Current limitation

`packages/database/migrations/007_supabase_auth_sync.sql`'s `on_auth_user_created` trigger syncs
a new Supabase Auth user into `public.users`, but nothing creates a matching row in
`memberships`. Without one, `apps/api/src/server.ts`'s `AUTH_MODE=managed` `preHandler` hook
(the JWT-verification step) returns `403 FORBIDDEN "No business membership exists for this
account."` on every single request, for every route — the account exists but is entirely
unusable. Confirmed by reading `scripts/managed-auth-smoke.ts`: Codex's own managed-auth
verification script only works around this by connecting to the database directly with the
service-role key and inserting the membership row itself after creating the test user, which
has no frontend equivalent (the anon key the frontend uses cannot write to `memberships`, and
shouldn't be able to).

## Proposed change

One of:

- A trigger or API-side hook that inserts a `customer` membership automatically on
  `auth.users` insert (mirroring `007_supabase_auth_sync.sql`'s existing pattern), if
  self-serve customer signup is the intended flow; or
- An admin-only "invite" or "create account" endpoint the business uses to provision
  mechanic/admin (and optionally customer) accounts explicitly, if open self-registration
  isn't intended for a small business like this one.

This is a product decision (open signup vs. provisioned accounts) as much as a technical one —
flagging both options rather than assuming either.

## Impacted screens

None yet — `apps/web/src/routes/SignIn.tsx` deliberately ships sign-in only, with no sign-up
form, specifically because of this gap (see the comment in `apps/web/src/lib/supabaseClient.ts`).
A sign-up screen is the natural next frontend piece once this is resolved.

## Compatibility

Additive.

## Acceptance checks

- A freshly created Supabase Auth user (however it's provisioned) has exactly one `memberships`
  row before their first API call, so `GET /session` succeeds instead of 403ing.
- Whichever path is chosen, the frontend team is told the exact mechanism (trigger vs.
  endpoint + payload shape) so the sign-up screen can be built against it.
