# CR-013: GET /mechanics returns duplicate rows and isn't scoped to a business

**Requester:** Claude (frontend)
**Status:** implemented

## User need

A customer picking a mechanic to book needs to see each mechanic once, and only mechanics that
actually work for this business.

## Current limitation

Previously, `packages/database/src/repositories.ts`'s `createBookingRepository.listMechanics` ran
`SELECT u.id, u.email AS "displayName" FROM users u JOIN memberships m ON m.user_id = u.id WHERE
m.role = 'mechanic' ORDER BY u.email` — no `business_id` filter at all. Confirmed live via curl:
`GET /mechanics` for `customer-demo` returned the same mechanic (`mechanic-demo@local.test`)
**four times**. Two problems in one query: (1) no `DISTINCT`/business scoping means a user with
more than one `mechanic` membership row shows up once per row, and (2) more seriously, nothing
restricts results to the calling customer's own business — in a real multi-tenant deployment this
would leak other businesses' mechanics into the picker.

## Proposed change

Scope the query to the caller's business (join through `memberships` on the caller's own
business id, the same pattern `POST /admin/memberships` already uses to find the calling admin's
business) and `DISTINCT` (or `GROUP BY`) on `u.id`.

## Impacted screens

`Booking` (`/book`) — the frontend works around the duplicates by deduplicating the mechanic list
client-side (by id) before rendering the picker, so the immediate symptom doesn't reach the UI,
but the cross-tenant scoping gap isn't something the frontend can fix.

## Compatibility

Additive — response shape (`{id, displayName}[]`) is unchanged, just correctly filtered/deduped.

## Acceptance checks

- `GET /mechanics` returns each mechanic exactly once.
- `GET /mechanics` never returns a mechanic who isn't a member of the caller's own business.

## Implementation

The repository now receives the authenticated customer id, joins mechanic memberships to the
customer's business membership, and uses `DISTINCT` to prevent duplicate rows. The response shape
and endpoint remain unchanged.
