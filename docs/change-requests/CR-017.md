# CR-017: `POST /service-requests` accepts `attachmentIds` but silently discards it

**Requester:** Claude (frontend)
**Status:** open — a real gap found while wiring real photo uploads

## User need

A customer who adds photos in "Tap Your Trouble" needs their mechanic to actually see those
photos on the resulting service request.

## What already works (live-verified 2026-09-11)

The upload endpoints themselves are correctly implemented and now fully live-verified end to
end: `POST /uploads` (initiate — validates file type/size, creates a durable `upload_references`
row, requests a real signed upload URL from Supabase Storage), a direct `PUT` of the file bytes to
that signed URL, and `POST /uploads/{id}/complete` (verifies the object landed in storage, flips
status to `ready`). All three legs tested with a real file against a real private bucket; also
tested and confirmed correct: 409 `UPLOAD_NOT_READY` when completing before the bytes are
actually uploaded, 404 for a nonexistent/not-owned upload id, 422 for a disallowed content type.

One environment gap found and fixed along the way, with the user's explicit go-ahead: the bucket
named in `SUPABASE_STORAGE_BUCKET` (`repair-evidence-private`) didn't exist yet in this dev
environment's connected Supabase project — confirmed via `GET /storage/v1/bucket` returning `[]`.
Created it (private, 25 MB size limit, `image/jpeg`/`image/png`/`image/webp`/`video/mp4` allowed
— matching `POST /uploads`'s own Zod validation exactly) via the Storage admin API using the
service-role key already present in `.env`. Not a code change; a one-time setup action on the
user's own Supabase project, done with explicit confirmation first.

## Current limitation

`POST /service-requests`'s Zod schema (`requestSchema` in `apps/api/src/server.ts`) accepts an
optional `attachmentIds: string[]`, and `apiAdapter.ts`'s `createServiceRequest` already sends it
— but `packages/database/src/repositories.ts`'s `createServiceRequestRepository.create` never
reads it: the function's own parameter type doesn't even include it, and the `INSERT INTO
service_requests` statement has no attachment-related column. Confirmed live: submitted a request
with a real `attachmentIds` array, got back a normal success response with no trace of the
attachment — it's accepted by validation and then silently dropped, not an error, not a no-op the
frontend can detect. `GET /admin/service-requests` (the only other read of a service request)
also selects no attachment/photo column at all, so there is currently no way, anywhere in the
API, for anyone to see which uploads belong to which request.

## Proposed change

Add an `attachmentIds` (or similar join table, e.g. `service_request_attachments`) relationship
so `createServiceRequestRepository.create` actually persists the linkage, and surface it on
`GET /admin/service-requests` (and anywhere else a mechanic/admin reviews a request) so the
uploaded photos are actually visible where they're needed.

## Impacted screens

`Intake` (`/intake/:category`) — the photo step now performs real uploads and sends the resulting
ids, but honestly discloses ("aren't visible to your mechanic within this request yet") that
they don't attach to anything yet, rather than implying a working attachment feature.

## Compatibility

Additive — no existing behavior changes; this only adds a missing linkage.

## Acceptance checks

- A service request submitted with `attachmentIds` durably links those uploads to the request.
- `GET /admin/service-requests` (or wherever a mechanic reviews a request) includes enough to
  retrieve/display the linked photos.
