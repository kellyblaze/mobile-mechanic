# CR-006: List pending service requests for admin quote issuance

**Requester:** Claude (frontend)
**Status:** open

## User need

An admin needs to issue a quote against a customer's service request (`POST /admin/service-requests/{id}/quotes`). To do that, they need to know which service requests are awaiting a quote and, per `QuoteInput`'s required `customerId`, which customer each one belongs to.

## Current limitation

`packages/contracts/openapi.yaml` has no `GET /admin/service-requests` (or similar) listing operation — only the single-resource `POST /admin/service-requests/{id}/quotes`. `GET /admin/jobs` lists jobs, not service requests, and a service request doesn't yet have a job (or `customerId`) associated with it until a quote exists. There is currently no endpoint the admin UI can call to discover a service request's id or its customer id.

## Proposed change

- `GET /admin/service-requests`: list service requests, filterable by status (e.g. `pending_quote`), returning at least `id`, `customerId`, `category`, `symptoms`, `notes`, and `createdAt`.

## Impacted screens

`AdminIssueQuote` (`/admin/quotes/new`, `apps/web/src/routes/AdminIssueQuote.tsx`) — currently requires the admin to manually type in the service-request id and customer id, with no way to look either up from the UI. This is a genuine, disclosed gap (see the in-app copy on that screen and `docs/integration-status.md`), not a guessed workaround.

## Compatibility

Additive.

## Acceptance checks

- `GET /admin/service-requests` enforces admin-only access, matching the existing `POST /admin/service-requests/{id}/quotes` and `GET /admin/jobs` authorization pattern.
- Response includes enough fields (`id`, `customerId`) for the frontend to populate a picker and remove the manual-entry fields on `AdminIssueQuote` with no other layout changes once it ships.
