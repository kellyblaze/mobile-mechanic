# CR-011: No endpoint lists mechanics for a customer to book

**Requester:** Claude (frontend)
**Status:** open

## User need

A customer booking a service needs to pick which mechanic they're booking with (or at least see
who's available), rather than the frontend having to already know a mechanic's UUID.

## Current limitation

Grepped every route registered in `apps/api/src/server.ts` (`app.get`/`app.post`/etc.) — there is
no `GET /mechanics` or equivalent. `GET /availability` and `POST /booking-holds` both require a
`mechanicId` (a raw UUID, `z.string().uuid()`), but nothing in the API surfaces which UUIDs are
valid mechanics for the business. The only reason the frontend can supply one at all right now is
that this business's dev seed data happens to have exactly one mechanic, and its id was found via
`GET /session` with the `mechanic-demo` dev header — not something a real customer could ever do.

## Proposed change

A `GET /mechanics` (or `GET /business/staff`) operation, admin- or customer-readable, returning
at least `id` and a display name for each mechanic in the business — enough for a real picker.

## Impacted screens

The new `Booking` screen (`/book`, built this checkpoint) currently hardcodes the one seeded
mechanic id with an in-code comment explaining why, mirroring the same honest-default pattern
`RepairRoom.tsx` already uses for the seeded job id. Once this ships, that hardcoded default
becomes a real picker.

## Compatibility

Additive.

## Acceptance checks

- `GET /mechanics` returns every mechanic membership for the caller's business, with enough
  identifying info (name, not just a UUID) for a customer-facing picker.
