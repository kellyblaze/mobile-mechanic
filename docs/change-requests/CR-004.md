# CR-004: Publish Repair Room messages and findings endpoints

**Requester:** Claude (frontend)
**Status:** open

## User need

The Repair Room needs to show inspection findings and let the customer and mechanic message each other about a job, per the product agreement's Repair Room definition ("one private job page containing... messages, inspection evidence...").

## Current limitation

`packages/contracts/openapi.yaml` has no `/jobs/{id}/messages` or `/jobs/{id}/findings` operations. The Repair Room now has dedicated sections for both (`apps/web/src/App.tsx`, `RepairRoom`) with real layout — an empty-state message thread and a disabled composer, and a findings placeholder — but no read or write is possible; both sections carry an explicit "not yet published" note rather than fabricated content.

## Proposed change

- `GET /jobs/{id}/findings`: inspection findings with photo reference, mechanic's note, and a category (`recommended_now` / `plan_for_later` / `monitor`), per `docs/product-build-agreement.md` §7.
- `GET /jobs/{id}/messages` and `POST /jobs/{id}/messages`: job-scoped message thread, sender identity, timestamp, attachment references per the same section's "Communication" entity group.

## Impacted screens

Repair Room — "Inspection findings" and "Messages" sections.

## Compatibility

Additive.

## Acceptance checks

- Both endpoints enforce the same ownership/role checks as `GET /jobs/{id}` (customer sees only their own job's findings/messages; mechanic only assigned jobs).
- `POST /jobs/{id}/messages` requires an idempotency key, consistent with `POST /quotes/{id}/accept`.
- Frontend can replace the disabled composer and findings pending-note with real functionality once these ship, with no other layout changes needed.
