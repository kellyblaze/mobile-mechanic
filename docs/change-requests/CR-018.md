# CR-018: No way to view an uploaded photo's content; invalid attachments 500 instead of 4xx

**Requester:** Claude (frontend)
**Status:** open — two real gaps found while wiring CR-017's frontend consumption

## User need

A mechanic or admin reviewing a service request needs to actually see the customer's photos, not
just know a count exists.

## Current limitation 1: no way to retrieve an uploaded file's content

`GET /admin/service-requests` and `POST /service-requests`'s own response both now correctly
return `attachmentIds` (CR-017, resolved — confirmed live), but there is no `GET /uploads/{id}`
for metadata and no endpoint that returns a signed *read* URL for an already-uploaded private
object (grepped `apps/api/src/server.ts` for any such route — none exists; only the write-side
`POST /uploads` and `POST /uploads/{id}/complete`). So the frontend can display how many photos
were attached, but has no way to render a thumbnail, link, or even a filename for any of them.
`AdminIssueQuote` (where an admin reviews a request before quoting) currently just shows a count
with an honest note that the photos aren't viewable there yet.

## Proposed change 1

A `GET /uploads/{id}` (metadata: fileName, contentType, sizeBytes) and/or a signed, short-lived
*read* URL endpoint (mirroring the existing write-side signed-upload pattern), scoped so only an
admin/mechanic on the associated job/request — or the owning customer — can retrieve it. Never a
public URL; the bucket is private for a reason.

## Current limitation 2: an invalid attachment reference 500s instead of a proper 4xx

`createServiceRequestRepository.create` (`packages/database/src/repositories.ts`) validates that
every `attachmentIds` entry is a real, owned, `status: 'ready'` upload, and correctly rejects the
request if not — but it does so by `throw new Error('INVALID_ATTACHMENTS')`, and the route handler
(`apps/api/src/server.ts`'s `POST /service-requests`) has no try/catch around the call, so
Fastify's generic `setErrorHandler` catches it and returns a plain `500 INTERNAL_ERROR` with no
detail (confirmed live via curl: submitted a real, nonexistent attachment id, got back
`{"error":{"code":"INTERNAL_ERROR","message":"The server could not complete the request."}}`).
Every other validation failure in this API — including the same route's own vehicle-ownership
check just above it — returns a proper typed 4xx. This one alone doesn't.

## Proposed change 2

Catch `INVALID_ATTACHMENTS` in the route handler (matching the existing pattern used for the
booking-hold conflict code) and return a real `422 VALIDATION_ERROR` (or `403`, if "not yours" is
the more common real cause) instead of a 500.

## Impacted screens

`Intake` (`/intake/:category`) only ever sends ids it has itself confirmed uploaded, so this is a
rare path in normal use — not something requiring a frontend workaround, just an honest backend
fix. `AdminIssueQuote` (`/admin/quotes/new`) shows an attachment count but can't render the
photos themselves until limitation 1 is addressed.

## Compatibility

Both additive — a new read endpoint, and a stricter (not looser) error response for an existing
failure case.
