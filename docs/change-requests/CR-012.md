# CR-012: A booking hold never converts into an appointment or job

**Requester:** Claude (frontend)
**Status:** implemented

## User need

After a customer holds a time slot, it needs to actually turn into a real, confirmed
appointment (and eventually a job) — a hold that just sits there forever isn't a booking.

## Current limitation

Grepped every route in `apps/api/src/server.ts` — `POST /booking-holds` inserts into
`booking_holds` (status `'active'`) and nothing else. There is no route that reads a
`booking_holds` row and creates an `appointments` row from it, despite
`packages/database/migrations/002_booking_payments_and_media.sql` adding an `appointments.hold_id`
column specifically to link the two. `booking_holds.status` has a `'converted'` value in its
check constraint, implying this was intended, but nothing sets it. Confirmed live: created two
real holds via `POST /booking-holds` this checkpoint; neither produced any visible appointment or
job anywhere in the app.

Also flagging, not filing separately since it's the same underlying gap: `GET /availability`
(`apps/api/src/server.ts`) only queries the `appointments` table, never `booking_holds` — so a
slot with a real, active, unexpired hold on it still reports `available: true`. Confirmed live
through the actual `Booking` screen: checked a slot (available), held it, then re-ran the same
availability check against the exact same window — still `available: true`, hold and all. Two
different customers could hold the identical slot right now with nothing catching it. Related:
the overlap-prevention exclusion constraint added in
`packages/database/migrations/005_booking_hold_overlap.sql` also did not block a real overlapping
hold when tested live via curl (two holds for the same mechanic and overlapping windows both
returned 201, not the expected 409) — worth checking whether that migration has actually been
applied to this dev database.

## Implemented change

Some path — a scheduled sweep, or an explicit "confirm hold" endpoint — that turns an active,
unexpired hold into a real `appointments` row (`hold_id` set), and presumably expires/cancels
holds that pass their `expires_at` without being confirmed.

## Impacted screens

The new `Booking` screen (`/book`, built this checkpoint) is honest about this: after creating a
hold, it tells the customer the slot is held but not yet a confirmed appointment, rather than
claiming the booking is complete.

## Compatibility

Additive.

## Acceptance checks

- After whatever "confirm" trigger is chosen, a previously-active hold's slot appears as a real
  appointment the customer (and eventually a job the assigned mechanic) can see.
- An expired, unconfirmed hold no longer blocks that time slot for other customers.
- Until a hold converts or expires, `GET /availability` reports that window as unavailable —
  a hold should mean something to a second customer checking the same slot, not just the first.
- `GET /availability` now expires stale active holds before checking and includes overlapping active `booking_holds` alongside appointments.
- A live hold followed by an identical availability check returned `available: false` with one conflict.
- `POST /booking-holds/{id}/confirm` now converts an active customer hold into a confirmed appointment and marks the hold `converted`.

Appointment-to-job creation is implemented in the same confirmation transaction: the endpoint
returns both the confirmed appointment and a `scheduled` job. The complete live customer flow was
verified through the frontend. Cancellation and rescheduling are separate policy-dependent work,
not part of this change request.
