# CR-016: Reschedule an appointment through a replacement booking hold

**Requester:** Product decision
**Status:** implemented and verified by dedicated live PostgreSQL journey

## Policy

- Customers, assigned mechanics, and admins may reschedule.
- Customers and mechanics require at least two hours before the existing appointment.
- Admins may override the two-hour cutoff for future appointments.
- Refunds are never automatic.
- The existing appointment becomes `rescheduled`.
- The existing job remains attached to the work and moves to the replacement appointment.

## Contract

`POST /api/v1/appointments/{id}/reschedule`

Request body:

```json
{ "holdId": "uuid", "expectedVersion": 1, "reason": "optional" }
```

The replacement hold must belong to the same customer, target the same mechanic, be active and
unexpired, and be locked with the appointment in one database transaction. The response returns
the new confirmed appointment. Stale versions return `409 STALE_VERSION`; invalid holds return
`409 BOOKING_HOLD_INVALID`; cutoff violations return `409 RESCHEDULING_CUTOFF`.

## Implementation

Migration `011_appointment_rescheduling.sql` adds the relationship and audit metadata. The
repository transaction creates the replacement appointment, marks the original `rescheduled`,
updates the job’s appointment reference, converts the hold, and writes an audit event.

## Follow-up verification

The dedicated real-PostgreSQL journey covers success, stale version, wrong customer hold,
cutoff, admin override, job reassignment, and authorization matrix behavior.
