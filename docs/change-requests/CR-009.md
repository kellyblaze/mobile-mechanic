# CR-009: POST /payments has no way to link to an invoice, and nothing marks an invoice paid

**Requester:** Claude (frontend)
**Status:** implemented

## User need

A customer with an open invoice needs to pay it, and the invoice needs to reflect that it's
been paid afterward — both for the customer to see and for the business's own records.

## Current limitation

`packages/database/migrations/002_booking_payments_and_media.sql`'s `payment_attempts` table
already has an `invoice_id uuid` column, but `apps/api/src/server.ts`'s `POST /payments` handler
never sets it — the `INSERT INTO payment_attempts` column list omits `invoice_id` entirely, and
the request body schema (`{amountMinor, currency, idempotencyKey}`) has no `invoiceId` field for
the frontend to even supply one. The Stripe webhook handler (same file) only updates
`payment_attempts.status` on `payment_intent.succeeded` — it never touches `invoices.status`.
Confirmed by reading both handlers directly, and by grepping the whole file for `invoiceId`/
`invoice_id` (no other route references either). Net effect: a customer can complete a real
Stripe payment and the invoice they paid will still show `status: "open"` afterward, with no
automatic path to `"paid"`.

## Proposed change

- Add an optional `invoiceId` to `POST /payments`' request schema; validate it belongs to the
  calling customer and set it on the `payment_attempts` insert.
- On `payment_intent.succeeded` in the webhook handler, if the matched `payment_attempts` row
  has a non-null `invoice_id`, update that invoice's `status` to `'paid'` in the same statement
  (or a follow-up query in the same handler).

## Impacted screens

The new invoice payment flow (`apps/web/src/routes/PayInvoice.tsx`, built this checkpoint) ties
a Stripe PaymentIntent to a specific invoice by amount/currency only, with no server-side
linkage. It discloses this honestly in the UI ("this invoice may not update to paid
automatically yet") rather than claiming a false success state. Once this CR ships, that notice
can come out and the invoice list can simply refetch after a successful payment.

## Compatibility

Additive — `invoiceId` optional keeps existing callers (none besides the frontend today) working.

## Acceptance checks

- `POST /payments` with a valid `invoiceId` records it on the resulting `payment_attempts` row.
- After the corresponding Stripe webhook event is processed, `GET /invoices` for that customer
  shows the invoice with `status: "paid"`.
- An `invoiceId` belonging to a different customer is rejected (403 or 422, not silently ignored).

Implemented in contract version 1.6.0. Payment attempts store `invoice_id`, and successful Stripe payment webhooks mark the linked invoice paid.
