# CR-014: Admin monitoring proxy endpoints

**Requester:** Claude (frontend)
**Status:** open

## User need

The client needs an admin-only monitoring area inside the Mobile Mechanic app itself, so they
don't have to sign in to GlitchTip separately to see error/incident status, webhook health,
payment reconciliation lag, and booking conflicts.

## Current limitation

Grepped the whole repo for `monitoring` — no route exists in `apps/api/src/server.ts`, no schema
in `packages/contracts/openapi.yaml`. The frontend cannot call GlitchTip directly (no org token
belongs in browser code, and GlitchTip's API isn't scoped for that), so there is no way to build
this against anything real yet. Built entirely in explicit `MOCK MODE` for now — see
`apps/web/src/lib/monitoringMockData.ts` and the four new `Monitoring*` route files, all visibly
labeled and never claiming real data.

## Proposed change

A Mobile Mechanic API proxy in front of GlitchTip (never GlitchTip called directly from the
browser), admin-only:

- `GET /admin/monitoring/overview` → `MonitoringSummary`:
  ```ts
  type MonitoringSummary = {
    environment: string;
    release?: string;
    api: { status: 'healthy' | 'degraded' | 'down'; checkedAt: string };
    issues: { open: number; critical: number; last24Hours: number };
    webhooks: { failed: number; oldestPendingAt?: string };
    reconciliation: { unpaidSucceededPayments: number; oldestLagMinutes?: number };
  };
  ```
- `GET /admin/monitoring/issues` — query params: `severity`, `status`, `environment`, `release`,
  cursor-based pagination (`cursor`, `limit`). Response: a page of issue summaries (id, title,
  severity, status, environment, release, count, lastSeenAt) plus a next-cursor.
- `GET /admin/monitoring/issues/{id}` — issue detail: message, route/transaction, timestamp,
  event count, and a stack-trace summary. Per the security requirements below, this must never
  include a GlitchTip DSN, and any customer-identifying fields (email, phone, VIN, payment ids,
  request payloads) must be redacted/masked server-side before this reaches the frontend — the
  frontend has no way to redact what it's never sent.
- `GET /admin/monitoring/webhooks` — webhook delivery status (failed count, oldest pending).
- `GET /admin/monitoring/reconciliation` — payment reconciliation lag (unpaid succeeded payments,
  oldest lag in minutes).
- `GET /admin/monitoring/uptime` — uptime monitor status.

## Impacted screens

Four new admin routes, all currently mock-only: `/admin/monitoring` (overview),
`/admin/monitoring/issues` (list) and `/admin/monitoring/issues/:id` (detail),
`/admin/monitoring/operations`. All four render a visible "MOCK MODE" notice and will switch to
real data with no other layout changes once these endpoints ship.

## Compatibility

Additive.

## Acceptance checks

- Every operation above is admin-only (403 for customer/mechanic, matching the existing
  `GET /admin/jobs` authorization pattern).
- `GET /admin/monitoring/issues/{id}` never includes a GlitchTip DSN or any of: Stripe secret
  keys, webhook signing secrets, Supabase service-role keys, access tokens, signed upload URLs,
  raw customer-upload contents, or unredacted customer email/phone/VIN/payment identifiers.
- `GET /admin/monitoring/issues` supports cursor-based pagination and the filters listed above.
