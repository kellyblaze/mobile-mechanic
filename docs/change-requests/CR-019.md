# CR-019: Global managed-mode auth preHandler blocks the one route meant to be public

**Requester:** Claude (frontend), relaying findings reported against staging
**Status:** open — confirmed root cause by reading the real server code, not fixed (backend, off-limits)

## User need

`GET /service-catalog` needs to actually work without authentication — it's the Home page's
service listing, shown before anyone has signed in or picked a dev role.

## Current limitation

`GET /api/v1/service-catalog`'s own handler (`apps/api/src/server.ts`) has no `auth()` call and
correctly returns public fixture data by design:

```ts
app.get('/api/v1/service-catalog', async () => ({ data: fixtureState.services, meta: {...} }));
```

But a global `preHandler` hook, registered only when a real database is configured
(`if (database) app.addHook('preHandler', ...)`), runs before every route handler and — when
`AUTH_MODE=managed` — rejects any request without a valid `Authorization: Bearer` header,
regardless of what the destination route actually requires:

```ts
if (database) app.addHook('preHandler', async (request, reply) => {
  const pathname = request.url.split('?')[0];
  if (pathname === '/api/v1/webhooks/stripe' || pathname === '/health') return;
  if (process.env.AUTH_MODE === 'managed') {
    const authHeader = request.headers.authorization;
    if (!jwks || !authHeader?.startsWith('Bearer ')) return reply.code(401).send({...});
    ...
  } else { /* dev-header rewrite, never blocks */ }
});
```

The exclusion list only covers `/api/v1/webhooks/stripe` and `/health` — `/api/v1/service-catalog`
isn't in it, so under `AUTH_MODE=managed` it 401s unconditionally, even though its own handler
never asked for auth. Confirmed by reading the code directly; not reproducible against this local
dev environment's usual `AUTH_MODE=development`, since that branch never returns 401 (it only
optionally rewrites dev headers) — this only manifests under managed mode, i.e. staging/production.

The companion symptom reported alongside this — `GET /vehicles` correctly 401ing on a managed-mode
deployment where the frontend has no Supabase session yet — is not a bug. `/vehicles` really does
require a real Bearer token under managed mode (by design), and a frontend build without
`VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` set at build time (Vite bakes `VITE_*` vars in at
build time, not runtime) will never have one to send — that's a deployment/environment
configuration gap for whoever manages the staging build pipeline, not a code defect in either
`apps/web` or `apps/api`. Flagging it here for visibility since it was reported alongside the real
bug, but there is nothing to fix in this repository for it.

## Proposed change

Add `/api/v1/service-catalog` to the preHandler's exclusion list, the same way
`/api/v1/webhooks/stripe` and `/health` already are. Worth a broader look, too: is
`service-catalog` the only route whose own handler is intentionally public but isn't in this
list? (Grepped every route handler in `server.ts` for one missing its own `auth()` call — this is
the only one; every admin-monitoring route already gates itself via `monitoringAdmin()`
regardless of this hook, so they're unaffected either way, just redundantly protected.)

## Impacted screens

`Home` (`/`) — the service catalog section would show a real error instead of the real data on
any managed-mode deployment, for every visitor, signed in or not, since a public marketing page
shouldn't require any auth at all.

## Compatibility

Additive — widening an exclusion list changes no other behavior.
