# CR-015: Job responses don't expose `appointmentId`, blocking a durable cancellation UI

**Requester:** Claude (frontend)
**Status:** open — a real gap found while building the appointment cancellation UI

## User need

A customer, mechanic, or admin looking at a job in Repair Room (or a job list) needs a way to
cancel the linked appointment from there — not only in the few seconds right after booking it.

## Current limitation

`POST /appointments/{id}/cancel` is implemented and live-verified working correctly (see below),
but nothing in the API ever hands the frontend an appointment id to cancel, except once,
transiently: `POST /booking-holds/{id}/confirm`'s response includes `job.appointmentId` (confirmed
live via curl — `packages/database/src/repositories.ts`'s `confirmHold` really does `INSERT INTO
jobs (appointment_id, ...) RETURNING ... appointment_id AS "appointmentId"`).

Every other read of a job omits it:
- `GET /jobs/{id}` (`jobFor()` in `apps/api/src/server.ts`) selects `id, customer_id, mechanic_id,
  status, version` — no `appointment_id`.
- `GET /admin/jobs` selects the same five columns, no `appointment_id`.
- `GET /mechanic-jobs` (whatever backs `MechanicJobs.tsx`) — same gap.
- There is no `GET /appointments` or `GET /appointments/{id}` at all.

So once a customer leaves the booking confirmation screen (closes the tab, comes back later, or
just navigates to Repair Room from a job list), the frontend has no way to discover which
appointment a job is linked to, and therefore no way to offer a cancel action anywhere except the
one moment right after `confirmBookingHold` succeeds. Built exactly that (see below) since it's
the only place currently possible — but it's a thin slice of what "cancel my appointment" should
mean.

## Proposed change

Add `appointment_id AS "appointmentId"` to the `jobFor()` SELECT (`GET /jobs/{id}`) at minimum, so
Repair Room can offer a cancel action for the job's linked appointment regardless of when the
customer/mechanic/admin arrives at that screen. Ideally also add it to `GET /admin/jobs` and
whatever backs `GET /mechanic-jobs`, so those list screens can do the same. A `GET
/appointments/{id}` (returning current status, so the UI can tell "already cancelled" apart from
"still cancellable" before even trying) would also help, but isn't strictly required if
`appointmentId` is exposed and the frontend just attempts the cancel and reads the real error.

## Impacted screens

`Booking` (`/book`) — ships a cancel action today, but only reachable in the same session,
immediately after confirming a hold. `RepairRoom` (`/jobs/:id`), `AdminJobs` (`/admin/jobs`), and
`MechanicJobs` (`/mechanic/jobs`) have no cancel action yet — blocked on this gap.

## Compatibility

Additive — adding a column to an existing SELECT changes no existing behavior.

## Live verification of what already works

`POST /appointments/{id}/cancel` itself is correctly implemented — verified live via curl for
all five real outcomes: success (200, returns the cancelled appointment with `cancelledAt`/
`cancellationReason`), re-cancelling an already-cancelled appointment (404 `NOT_FOUND`), a
non-participant actor (403 `FORBIDDEN`), a customer/mechanic within the two-hour cutoff (409
`CANCELLATION_CUTOFF`), and an admin bypassing the cutoff (200 success). No auth headers at all
correctly 401s.

One unrelated thing found and fixed along the way, not a code bug: this dev database was two
migrations behind (`009_appointment_cancellation.sql`, `010_upload_completion.sql` were present in
the repo but never applied here — the first cancel attempt 500'd with `column "cancelled_at" does
not exist`). Ran `pnpm db:migrate` (the existing, idempotent, already-committed migration runner)
to bring the local dev database current — no source file was touched.
